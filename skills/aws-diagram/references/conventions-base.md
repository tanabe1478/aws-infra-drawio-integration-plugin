# 既定の作図規約

全ビュー共通の規約。ビュー固有の決定は出力先の `conventions.md` に追記して上書きする。

## 何を描くか

図は「伝えたいこと」を決めてから描く。1 枚に全リソースを載せない。

- 1 ビュー = 1 つの関心事 (リクエスト経路 / 非同期処理 / CI/CD / 監視)
- ノードが 20 を超えたらビューを分ける
- IAM ロール・ログ設定・タグは、それ自体が主題でない限り載せない
- コードに存在しないリソースを推測で載せない

## 配置

レンダラが自動で決めるが、意図は次のとおり。`structure.yaml` の書き方で調整する。

- 流れは左から右。`edges` の連鎖で列が決まるので、主要な経路をつなげば自然に一直線になる
- 主要フローは各コンテナの先頭行を占有し、補助的なリソース (監視・スケジューラ・バックアップ) は下の行に回る
- 利用者・外部システムは AWS Cloud の外、左端に置く (`container` を指定しない)
- 列を固定したいときだけ `column` を使う。行は指定できない (宣言順で決まる)

## 枠 (containers)

- ネットワーク境界がある構成では `aws_cloud` → `region` → `vpc` → `availability_zone` → サブネット の順に入れ子にする
- サーバーレス中心で VPC を使わない構成では `aws_cloud` → `region` までで止める。空の VPC 枠を描かない
- パブリック/プライベートの別が主題なら `public_subnet` / `private_subnet` を使い分ける。そうでなければ `subnet` で足りる
- グローバルサービス (CloudFront、WAF、Route 53) はリージョンの外に置く。`generic` の枠でまとめてもよい

## 線 (edges)

- 向きは「呼ぶ側 → 呼ばれる側」。データが逆に流れる場合は `label` で補う
- `trigger` は必ず付ける。色と線種が意味に対応する (対応表は `structure-spec.md`)
- 同じ意味の線に別の色を使わない。新しい意味が必要なら `layout.yaml` の `triggers` に語彙を足す
- 双方向の通信は 2 本の線に分けず、1 本に `label` で書く

## ラベル

- ノード名は実際のリソース名 (`orders-api-handler`)。Terraform の識別子 (`aws_lambda_function.orders_api`) は使わない
- HTML タグを書かない。`<br>` は改行にならず文字列として表示される
- 補足は `description` に書く。図では tooltip になり、線やアイコンを汚さない

## 色

AWS 公式アイコンの色をそのまま使う。サービスごとの色を独自に付け替えない。
枠の色はコンテナの種類で決まっている (VPC は紫、リージョンは青の破線、パブリックサブネットは緑)。

環境の別 (本番/検証) を色で表したい場合は `generic` の枠を使い、その決定をビューの `conventions.md` に書き残す。
